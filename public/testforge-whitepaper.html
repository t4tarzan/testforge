Part One

What TestForge actually is.

A pre-merge analyzer for code your team didn't entirely write — the increasing share now produced by AI assistants, copilots, and agents — that surfaces the static issues a human reviewer or a downstream runtime tool would catch only after the diff landed.

TestForge is, mechanically, a Babel-based static analyzer with a taint-tracking engine and a twenty-one-dimension policy layer. Pointed at a repository or branch, it parses every JavaScript and TypeScript file into an AST, walks the trees for the patterns each dimension defines, and produces a ranked report with one-line fixes attached. The whole pass typically completes in under thirty seconds.

The product runs in three legible stages:

  1. Parse — Babel reads every .js / .jsx / .ts / .tsx, building an AST per file. Untouched language regions parse without TypeScript checks, so the analyzer never blocks on type errors the reviewer hasn't fixed yet.
  2. Analyze — Each of the twenty-one dimensions walks the AST under its own rules. Cross-cutting dimensions (security, agentic) maintain a taint map: tainted sources (req.params, req.body, req.query) flow through function calls to sensitive sinks (SQL, eval, exec, innerHTML).
  3. Report — Findings are ranked by severity, mapped to OWASP / DORA / WCAG categories where applicable, and returned with line-precise locations and one-line fixes.
TestForge does not run your code. It reads it — once, in roughly thirty seconds — and tells you what your runtime tools will find an hour or a quarter from now.

The design choice that defines the rest of the product is what TestForge doesn't do. It does not load-test. It does not fuzz at runtime. It does not run Robot Framework. It pairs with k6, Locust, ZAP, Stryker, Pitest, Gremlin, Litmus, Chaos Mesh — handing them a much smaller surface to cover because the static layer has already been walked.

Part Three

Architecture — AST, taint, MCP.

Three layers do all of the work: a Babel parser shared across every dimension, a taint engine for the security and agentic dimensions, and an MCP-compatible server for the editor and agent integrations that drive most of TestForge's traffic.

§ The parse layer

One Babel pass per file builds the AST. TypeScript files parse with the @babel/preset-typescript plugin without invoking the TypeScript compiler — the analyzer never blocks on type errors the reviewer hasn't fixed yet. Each dimension receives the AST plus the raw source string; dimensions never re-parse.

§ The taint engine

For the security and agentic dimensions, sources and sinks are configured per rule. Tainted values flow through:

  • Variable assignment and destructuring
  • Function calls (taint propagates from arguments to return values for known sink-adjacent functions)
  • Object property access (per-property taint)
  • Template literals (any tainted interpolation taints the whole string)

The trace is line-precise — every finding includes the source line and the sink line, so a reviewer can follow the flow without re-running the tool.

§ The MCP server

TestForge ships an MCP-compatible server (testforge-mcp.fly.dev) that exposes the analyzer as tools any MCP client can call — Claude Desktop, Cursor, Aider, custom agents. The web app is one of the clients. Every other surface (the CLI, the editor integrations, the pipeline runners) goes through the same MCP contract.

§ The billing layer

Free runs are bounded to a per-calendar-month quota via a single gate (api/_gate.js) read live from the user record; a successful Stripe webhook updates the plan in real time. The save path checks the gate server-side before persisting a run, so the quota is bypass-proof regardless of which client started the run.

Privacy posture

TestForge defaults to local-first. The MCP server hashes paths and strips identifier-bearing tokens before any cloud AI call is made. Teams that opt into cloud AI for the deepest dimensions (vision & goal alignment, agentic concurrency) get a PII-anonymized request — repo paths become hashes, identifiers become opaque tokens, the model never sees a real customer name.

Part Four

Every dimension, opened.

Twenty-one numbered blocks. Each one names the dimension, the deepening pass that shipped its current depth, the patterns the analyzer actually walks for, and the runtime tool it hands off to.

01Scopev0.10 · pass 2

Requirement coverage & boundary validation.

Parses PRDs, user stories, and acceptance criteria and maps each requirement against the codebase to identify gaps. Boundary validation walks each input parameter for edge conditions, null inputs, and limit values that human reviewers tend to skip.

  • Automatic requirements extraction from PRDs and issue trackers
  • Coverage-gap identification with risk-weighted prioritization
  • Boundary value analysis on every input parameter
  • Requirement-to-test traceability matrix
Pairs with Jest / Vitest for the actual assertions; PRD parsers for ingestion.
02Vision & Goalv0.11 · pass 3

Business-goal alignment & outcome prediction.

Measures whether the implemented behavior actually achieves the business goal, not just whether it returns correct values. Extracts goals from product documentation, maps features to outcomes, and validates user journeys against intended paths.

  • Business-goal extraction from product documentation
  • Feature-to-outcome mapping with scoring
  • User-journey validation against intended paths
  • ROI impact estimation per feature
Pairs with Amplitude / Mixpanel / your product analytics stack.
03Feature Matrixv0.12 · pass 4

Traceability matrices & impact analysis.

Auto-generates and maintains a matrix linking requirements, tests, code, and deployments. On change, the analyzer walks the matrix to identify every affected component, shrinking regression scope.

  • Automatic traceability-matrix generation
  • Change-impact analysis with affected-component list
  • Cross-reference validation between requirements and tests
  • Regression scope minimization
Pairs with Linear / Jira for the requirement source-of-truth.
04Load & Scale Patternsv0.13 · pass 5

The code patterns your service needs to survive traffic.

Scans for the static patterns a service needs to survive load — rate-limit middleware on public endpoints, caching layers on hot paths, queue / backpressure handling, connection-pool sizing, and pagination on list reads. Pre-merge, not pre-incident.

  • Rate-limit middleware detection (express-rate-limit, fastify/rate-limit, custom)
  • Cache-layer presence (Redis, in-memory, HTTP caching headers)
  • Queue / backpressure handling detection
  • Connection-pool configuration scan
  • Pagination presence on list endpoints
Pairs with k6 / Locust / wrk for the actual load run — TestForge handles the static gaps.
05Predictive Risk Scoringv0.14 · pass 6

Risk score per file from complexity + churn signals.

Each file is scored on AST-derived cyclomatic complexity (McCabe), function length, parameter counts, dependency density, and — when git history is available — change-frequency churn. The output is a ranked heatmap so reviewers spend deep-review time on the files that earn it.

  • AST cyclomatic complexity per function (McCabe)
  • Function-length and parameter-count thresholds
  • Dependency density per module
  • Optional change-frequency signals from git log
  • Ranked risk heatmap for review prioritization
Pairs with CodeClimate / SonarQube for trend data over time.
06Security — SAST + Taint Trackingv0.15 · pass 7

Babel AST + taint flow across the OWASP Top 10.

The taint engine traces tainted sources (req.params, req.body, req.query) through function calls to sensitive sinks (SQL drivers, eval, exec, fs, child_process, innerHTML). Findings map directly to OWASP Top 10 categories with line-precise sink locations.

  • SQL / NoSQL injection via tainted-input flow
  • eval / Function() / vm.runIn* sink detection
  • XSS sinks: innerHTML, dangerouslySetInnerHTML, document.write
  • Hard-coded secret patterns (API keys, JWT, AWS keys)
  • CORS misconfig (wildcard origin + credentials true)
  • OWASP Top 10 coverage % per category
Pairs with OWASP ZAP / Burp Suite for the DAST layer at runtime.
07Visual Regressionv0.16 · pass 8

Computer-vision diff across breakpoints, devices, browsers.

Screenshots are captured across breakpoints, devices, and browsers, then compared pixel-by-pixel. Even a one-pixel shift is caught. Baseline management runs through an approval workflow so intentional changes don't accumulate noise.

  • Screenshot comparison across all configured breakpoints
  • AI-assisted visual-diff highlighting
  • Component-level isolation detection
  • Cross-browser visual-consistency checks
  • Baseline management with approval workflows
Pairs with Percy / Chromatic for hosted snapshot history.
08Accessibilityv0.17 · pass 9

WCAG 2.1 AA — automated coverage of the 57% that can be automated.

Industry research is consistent: roughly 57% of WCAG criteria can be checked automatically. TestForge ships the automated set — contrast ratios, keyboard navigation, screen-reader output, focus trap and order, ARIA correctness — and produces remediation suggestions for each finding.

  • Color-contrast ratio validation (WCAG AA / AAA)
  • Keyboard-navigation flow testing
  • Screen-reader output verification
  • Focus trap and order detection
  • ARIA attribute validation
  • Automated remediation suggestions
Pairs with axe-core / Pa11y; manual audit for the remaining 43%.
09Resilience Pattern Detectionv0.18 · pass 10

The patterns your code needs to survive partial failures.

Walks the AST for the patterns code needs to survive partial failures: retry-with-backoff, circuit breakers, request timeouts, idempotency keys, graceful degradation. Critical I/O paths missing these defenses are flagged before a chaos run finds them.

  • Retry-with-backoff pattern detection
  • Circuit-breaker library usage (opossum, polly, hystrix)
  • Request-timeout configuration scan
  • Idempotency-key handling on POST / PUT endpoints
  • I/O paths missing resilience guards flagged
Pairs with Gremlin / Litmus / Chaos Mesh for the live fault injection.
10Mutation-Score Estimatev0.19 · pass 11

Heuristic mutation score in seconds, not minutes.

Full mutation testing is the gold standard but takes minutes per file. TestForge estimates the score in seconds by analyzing assertion density, branch coverage in the test files, and the test-to-source ratio. Not as authoritative as a real Stryker run — close enough to flag weak suites pre-merge and pair with the heavier tool in CI.

  • Estimated mutation score per source file
  • Assertion-density signals from the test files
  • Branch-coverage signals
  • Surfaces suites with low mutation resilience
Pairs with Stryker / Pitest for confirmation on the files that earn it.
11Property-Basedv0.20 · pass 12

Invariant validation with intelligent input generation.

Instead of testing specific examples, you define properties — invariants that should hold for all inputs — and TestForge generates edge cases that a human writer would never produce. When a property fails, the engine shrinks the input to the minimal reproducer.

  • Property definition and invariant specification
  • Intelligent input generation (including edge cases)
  • Shrinking — minimal failing-case identification
  • Cross-property interaction testing
  • Regression-property validation
Pairs with fast-check / Hypothesis for the property runtime.
12Contractv0.21 · pass 13

Microservice API contract validation.

Walks provider and consumer contracts to ensure your microservices honor what they promise — both as producers and as callers. Breaking-change detection runs at the schema layer (OpenAPI, GraphQL, Pact) so breakages are caught before deployment, not in production.

  • Provider and consumer contract validation
  • OpenAPI / GraphQL schema compliance
  • Pact-compatible contract testing
  • Breaking-change detection with impact analysis
  • Consumer-expectation mapping
Pairs with Pact / OpenAPI tooling / GraphQL Inspector.
13Test Quality Analysisv0.22 · pass 14

Finds the ghost tests in your suite.

Most test suites contain ghost tests that look green but assert nothing. TestForge walks every parseable test file and flags .skip / xit / .todo (rot risk), .only / fit (silently kills sibling tests in CI), empty test bodies, and tests with zero recognized assertions. Supports eight frameworks.

  • AST-aware detection of it.skip / xit / it.todo
  • it.only / fit detection (these silently skip sibling tests)
  • Tests with no recognized assertion call
  • Empty test bodies (comments-only)
  • Tests importing nothing project-relative
  • Supports Jest, Vitest, Mocha, AVA, Tap, node:test, Testing Library, Chai
Pairs with your existing test runner — TestForge is a meta-check on the suite itself.

20Edge Case Generationv0.24 · pass 16

AST detection of the foot-guns that only surface at 3 AM.

The analyzer walks each parseable file looking for the JavaScript foot-guns that code review keeps missing. Each finding includes the line number and a one-line fix.

  • parseInt without radix (silent base-8 / hex bugs)
  • JSON.parse not wrapped in try (untrusted-input crashes)
  • Loose equality (==) on non-null comparisons

  • Endpoints without rate limits flagged for agentic risk
  • Unbounded list queries (missing LIMIT / pagination)
  • Synchronous I/O on high-traffic paths
  • Missing idempotency on POST endpoints
  • Retry-storm risk in client code
Pairs with k6 / custom agent-load scripts that simulate the concurrency profile.

Part Six

Tier 2 — Generate & Run.

Static findings answer "where is the risk?" Tier 2 answers the next question: "what does a test for it look like, and does it pass?" An LLM writes Vitest files for the top findings; a sandboxed runner executes them and ships the pass/fail back, all in under a minute.

The first product surface (Tier 1) reads code and reports gaps. The natural next step is to close the gap automatically — generate the tests that exercise the failure mode, run them, and tell the reviewer whether the fix works. Tier 2 is that loop, and it ships on top of the static layer rather than replacing it.

§ The three steps

  1. Select — the top-N findings (default N=3) across all dimensions, sorted by severity. The static report is the seed; we don't ask the LLM to discover what the AST already found.
  2. Generate — each finding goes to the LLM with a Zod-enforced JSON schema (filename, content, reasoning). The system prompt is strict: Vitest imports only, no project imports, ≥2 it() blocks (one demonstrates the foot-gun, one asserts the fix), no flakiness sources. Provider rotation: if Qwen rejects the schema or rate-limits, DeepSeek V4 Flash takes over silently. Both attempts are recorded.
  3. Run — the generated files drop into a pre-baked Docker container (node:22-slim + Vitest 3 + TypeScript 5). The bind mount is read-only, --network=none keeps the LLM-generated code air-gapped, --rm destroys the container the moment it exits. Vitest's JSON reporter writes structured pass/fail to stdout; we parse and return it.

§ Iteration — what's next

Day-3 Tier 2 is one-shot: generate → run → report. The natural evolution is the iteration loop — when a test fails, feed the failure back to the LLM with the relevant code snippet, ask whether the test or the code is wrong, and synthesize a patch. Repeat up to N=3 rounds. The static seed keeps each round scoped to specific findings, so the LLM cost stays bounded.

The sandbox stays the same. The change is one extra prompt-shape after each failed run, plus a state machine that tracks "test fixed", "code fixed", or "give up after N rounds." That ships separately when it ships.

§ Self-host vs managed

The local MCP server (npx @whitenoisenpm/testforge-mcp) has /generate-and-run open by default — users bring their own OpenRouter key and pay OpenRouter directly. No quota enforced. For the managed SaaS at testforge.run, Tier 2 is the Forge plan: 100 iterations per calendar month with Qwen + DeepSeek V4 Flash routing handled for the user. Free and Pro tiers receive a 402 on Tier 2 with a link to upgrade; Enterprise lifts the cap entirely.

Sandbox swap — today & tomorrow

Today the sandbox is local Docker (Colima on the hub, Docker Desktop on user machines). The runner spawn is one function — replacing it with a Fly Machines API call ports the same --rm, --network=none guarantees to managed infrastructure. Cold-start trades up from ~1-3 seconds locally to ~5-15 seconds on Fly, in exchange for "the user doesn't need Docker installed." Tier 3 would replace this with a RunPod GPU pod when the loop adds visual reasoning (screenshot diffing on Playwright runs).
